# ADR-013: Use the Print Page as the Single Source of Truth for PDF Generation

**Status:** Accepted

**Date:** 2026-07-26

---

# Context

WBOS generates PDF documents (invoices, quotations, credit notes, sales orders).

Previously, PDF generation used a separate HTML builder (`invoicePdfHtml.ts`) that duplicated the React component tree in plain strings. This led to drift: the printed page and the downloaded PDF looked different.

We needed a single source of truth.

---

# Options Considered

## Option 1: Server-side React rendering

Use `react-dom/server` (`renderToStaticMarkup` / `renderToString`) to render the React component to HTML in a route handler, then pass the HTML to Playwright.

**Rejected.** Next.js App Router explicitly blocks `react-dom/server` in route handlers at the bundler level. No workaround exists without ejecting or using a separate rendering service.

## Option 2: Independent HTML builder

Maintain a separate function that generates HTML strings matching the React component.

**Rejected.** Experience showed this duplicates layout logic and inevitably drifts. Every layout change requires updating two code paths.

## Option 3: Migrate the document engine to an HTML template engine

Replace React-based `DocumentEngine` components with plain HTML templates (e.g., Handlebars, EJS).

**Rejected.** This is a large rewrite that removes the benefits of React (component reuse, state management, hooks) and introduces a new rendering dependency. The document engine is also used for on-screen display, not just PDFs.

## Option 4: Playwright navigates to the live print page

Have Playwright open the browser print page URL (`/invoices/{id}/print`) and call `page.pdf()`.

This requires the print page to be accessible without a session cookie — Playwright runs in an isolated browser context with no Better Auth session.

---

# Decision

We chose **Option 4**: Playwright navigates to the print page URL using a short-lived signed token for authentication.

```
Browser Print Page
        ┃
        ┃ ┌──────────────────────────────────┐
        ┃ │ InvoiceDocumentContent           │
        ┃ │ (single React component)         │
        ┃ └──────────────────────────────────┘
        ┃
        ┣━━ Playwright (headless Chromium) ━━━ PDF
        ┃
        ▼
Signed download token (?token=xxx)
        │
        ▼
proxy.ts: verifyDownloadToken() → allow through
        │
        ▼
Print page: verifyDownloadToken() → render component
```

## Key design decisions

### 1. Signed tokens instead of cookie injection

Playwright cannot set HttpOnly / `SameSite` cookies via `context.addCookies()`. Instead, we generate a short-lived (5-minute) HMAC-signed token containing `{ invoiceId, organizationId, exp }` and pass it as a query parameter.

### 2. Token validation at two layers

- **proxy.ts**: Recognizes `?token=` on print routes (`/print`), calls `verifyDownloadToken()`, and allows the request through without requiring a session cookie. This prevents a redirect to `/sign-in` before the page component runs.
- **Print page component**: Independently re-verifies the token and uses `payload.organizationId` to fetch data. This keeps the page capable of authorizing itself if routing or middleware changes in the future (belt and suspenders).

### 3. Playwright sanity check

After `page.goto()`, the printer checks for the presence of `.print-page` (a selector rendered by `PrintLayout`). If it is absent (e.g., Playwright was redirected to `/sign-in`), the printer throws a clear error instead of silently generating a PDF of the login page.

### 4. Two PDF generation routes share the same code path

Both the authenticated route (`/api/invoices/{id}/pdf`) and the unauthenticated download route (`/api/invoices/download/{token}`) generate a signed token and call `generatePdfFromUrl(printUrl)`. They differ only in how the user is authenticated (session vs. token).

---

# Consequences

**Positive:**

- The React component (`InvoiceDocumentContent`) is the single source of truth for both on-screen display and PDF output.
- Layout changes automatically apply to both print and PDF.
- No duplicated HTML template code to maintain.
- Token-based auth is simple and avoids session cookie problems with Playwright.
- `proxy.ts` handles token recognition generically — any route ending in `/print` can opt in.

**Negative:**

- PDF generation requires the Next.js server to be running (Playwright requests a live URL). It cannot work during a static build.
- Playwright startup latency is incurred for every PDF. This is acceptable for on-demand generation but would need a background job architecture for bulk PDFs.
- The download token is a shared secret derived from `DOWNLOAD_TOKEN_SECRET`. Token expiry (5 minutes) limits reuse window.

**Neutral:**

- `generatePdfFromHtml()` is retained for quotations PDF, which still uses an in-memory HTML renderer. Future work may migrate quotations to the same print-page approach.
